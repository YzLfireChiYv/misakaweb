# 网页适配维护入口

本目录是随产品维护的工具资料。当前已有净化与过滤核心及九种按优化组实际裁剪的成品，开发测试版保留完整能力。评分和新WebDAV协议尚未实现。维护时优先保留用户数据、实际配置键及既有启停行为。

## 生成给网页版AI的材料

在产品目录运行：

```text
pnpm maintenance:index
pnpm maintenance:packet --module shortcut
pnpm maintenance:packet --setting S179
```

维护包默认写到忽略的本地临时目录，包含一份可上传的CONTEXT.md、manifest.json和相关源码。不要只提交编译后的完整脚本；它可用于复现，修改依据应是源码模块。包是待维修材料，不是通过验收的证明。

维护包是源码子集，不是可独立编译的完整仓库。执行构建时拉取包中Git提交对应的工程、按锁文件安装依赖，再应用修复；若有未提交改动，以包内源码哈希与改动列表识别实际输入，不假称仅凭Git提交即可复现。包包含锁文件和工作区配置的副本，避免重新解析版本范围造成环境差异。

`registry.json`记录模块路径、固定上游与逐文件基线哈希。路径对应只是来源线索，文本不同也不自动代表需要保留的设计差异；应结合实际改动判断。`index.generated.json`补充当前源码哈希、稳定设置编号与静态依赖。新增文件来源尚未确认时应明确标记，不能猜成上游或自有。

如发现现场问题，在开发脚本M06中点击“导出维护诊断”，将JSON作为可选证据输入。它只记录结构，不导出网页正文或页面地址/query，不读取名单、存储、Cookie或网络数据；不包含截图。打开设置面板可能改变焦点，诊断只是当时的结构样本，0命中不自动等于Bug。截图或失败步骤由用户另行提供，分享前注意账号与私人内容。

命令可以选模块、设置编号/配置键或源码文件；具体参数以工具`--help`为准。上游新提交应提供完整40位提交号，工具只生成对照链接，不假定上游已修复。首次来源基线由协调者核对，常规构建/维护包不依赖本机refs或OneDrive。

## AI应如何提交修复

1. 从问题、相关源码及固定上游对照确定影响范围。区分网站变化、我们本地改造导致的问题和缺少现场证据，说明推断。
2. 修改独立产品仓库，保留实际GM键、用户值、数据作用域和编号；名单、凭据和缓存不混为一种同步数据。评分/规则与页面解析分开，不把缺失数据当作0或命中。
3. 优先修改受影响的适配代码，借用上游小块实现时记录来源与本地差异，保留许可证；不要整文件覆盖我们的功能或引入完整上游运行时而未说明依赖。
4. 用完整脚本在受影响页面检查功能开启、关闭/恢复、重新进入/切换、必要的脚本共存。没有执行的检查标记未执行，不把类型检查通过当作网页兼容通过。
5. 交付补丁、原因、检查结果、未确认范围及需要现场补充的信息。网页AI无法执行浏览器/构建时仍可给出补丁，由有环境的一方完成验收后发布。

日常静态检查与构建由release:prepare和GitHub工作流执行；真实网页检查仍需运行对应浏览器测试或实机操作。现有`pnpm test:search`覆盖真实搜索与快捷入口共存，其他页面按实际受影响范围补检查，不预先建设巨大实验矩阵。

公开包不得包含私人备份、完整GM记录、原始HTML/HAR、用户目录或活动浏览器配置。工具只接受符合只读结构诊断协议的可选证据；任何自动读取或打包私人材料都不在默认流程内。
## 分包构建维护

维护材料同时包含 `config/build-profiles.json`、`scripts/pack-build.mjs`、`scripts/build-variants.mjs` 和 `PACKS.md`。修改页面规则时同时核对类目与功能组；新增未分类规则会停止成品构建。完整发布检查用 `pnpm release:prepare`，确保净化依赖保留且优化在所选成品中实际裁剪。
